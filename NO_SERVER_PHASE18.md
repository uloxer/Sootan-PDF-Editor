# Standalone phase18: compression, decompression and repair

The existing compression and repair tool forms now dispatch to lazy non-web `compress` and `repair` operations. `decompress-pdf` also has a fixed standalone route. No listener, helper installation or network use was added. Installed3.2.5, real Data and existing native windows were left untouched; this source checkpoint awaits final packaging.

`PdfCompression` contains the extracted original image identity/deduplication, resizing, JPEG-quality/grayscale and level/target-size algorithms. The legacy controller uses those same primitives and retains its existing optional Ghostscript/QPDF/ImageMagick branches. The private package currently contains Java, OCR Python/Tesseract and OCRmyPDF, but no GS/QPDF/ImageMagick executable. Standalone compression therefore uses the genuine Java image path, refuses line-art/linearize options explicitly, and keeps levels1–3 byte-identical when no grayscale operation is requested. Only image XObjects are recompressed; text/vector pages are not rasterized. Target size remains best effort, with escalation through level9 and original-byte fallback when the candidate is no smaller. It is not a guaranteed size ceiling.

`PdfRecovery` shares the existing PDFBox repair fallback and stream-decompression algorithm with legacy facades. Repair loads recoverable structure and saves a new document; it cannot recover missing page content or guarantee every damaged PDF is repairable. Stream decompression retains the source behavior of leaving an undecodable stream encoded. Its decoded allocation is limited to100MiB per stream; output streams use the existing bounded writer. Image decoding checks the existing100-million-pixel ceiling before decoding, and the native operations have a three-minute owned-process deadline. All standalone mutations require owner permission and reject signed inputs. Inputs remain read-only copies; host job cleanup/cancellation is unchanged.
