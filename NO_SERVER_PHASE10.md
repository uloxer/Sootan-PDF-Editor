# Standalone in-process Office conversions - phase 10

Verified 28 October 2026. Local review checkpoint: no push, installer replacement or changes to real Data/library/profile.

## Connected modes and compatibility

Plain PdfOfficeConversion contains the existing OfficeConversionService algorithms, format map, settings handling, table-content detection and legacy binary-PPT conversion. The Spring facade retains its configuration/default-engine routing. Plain PdfOfficeInput delegates to the same OfficeToPdf0.2.2 API; the existing OfficeToPdfService preserves legacy lifecycle/config/fallback behavior through that delegate. ZipBombGuard moves unchanged into the shared module under its original package; common callers remain compatible. No whole common/Spring module enters the worker.

| Capability | Actual library formats | Existing tool routes |
| --- | --- | --- |
| office-export | DOCX, DOC(RTF bytes), ODT, RTF, TXT, PPTX, PPT, ODP, XLSX, ODS | pdf/word, pdf/presentation, pdf/text, pdf/xlsx |
| office-import | DOCX, PPTX, XLSX, PPT, TXT, CSV, TSV | file/pdf |

These lists come from the cached0.2.2 API, not the broader artifact description. The UI retains its existing format matrix; library formats without an existing dropdown target are not new UI promises. The dynamic Convert processor enables available Office pairs and sends their exact options to the private worker. Explicit legacy LibreOffice engine requests are refused with a useful message; no helper fallback is attempted. Plain TXT remains the existing PDFTextStripper default; an explicit in-process engine selection uses OfficeConvert's TXT algorithm, and RTF uses the in-process writer. DOC output remains the legacy RTF-in-DOC-suffix behavior, not a binary DOC writer. DOC/XLS/ODF imports are not advertised by this actual importer enum.

PDF exports preserve the existing editable Office algorithms and defaults: tables enabled, pictureFallback=false, figure DPI150, compact pictures. They do not substitute whole-page raster output. XLSX/ODS select the existing table-sheet mode; XLSX without cells is refused instead of inventing extracted data. Selected page ranges are bounded and exported in requested order. These converters remain layout approximations from the existing library; this batch does not claim Microsoft Office rendering fidelity or support for every advanced Office feature.

## File, resource and process boundary

Imports reuse the existing indexed read-only selected-file grants and50 MiB/file cap, with exactly one selected Office member per job. Names/MIME are bounded metadata; no client filesystem path is used. Actual format is checked by a finite extension list plus OOXML ZIP signature/required package parts, or binary PPT OLE signature; text inputs reject obvious binary/archive signatures. Encrypted Office containers are not a connected input mode. Private staging writes only office-input.<allowlisted extension> inside the job. No ZIP entries are extracted as filesystem paths.

The retained ZipBombGuard enforces5000 entries,10 MiB per expanded entry and200 MiB expanded total before conversion. Duplicate/absolute/traversal/backslash entry names are refused. XML is parsed with DOCTYPE/external entities/schema access disabled. **All external relationships are explicitly refused**, including ordinary hyperlinks, with a fixed OFFICE_EXTERNAL_RESOURCE message explaining that linked resources must be embedded or links removed. This conservative compatibility limitation remains queued for a bounded library audit; silently dropping linked-image content was rejected. Original Office bytes are unchanged. No external resource, LibreOffice, global Office installation, helper or server is started.

PDF exports authenticate readable user credentials and require extraction permission; there is no blanket mutation-owner requirement for readonly export. Imports use the host-controlled bundled-font directory, not a JavaScript-selected path. Library conversion timeout is2 minutes; native Office jobs have a3-minute owned-process watchdog. Imports cap1000 pages/256 MiB scratch and refuse truncated/page-limited results. PDF exports cap1000 pages/100 MiB input and refuse outputs over256 MiB. Existing process-tree cancellation/cleanup remains active.

New POI/Log4j diagnostics exposed a real native boundary defect: a diagnostic appeared on stdout between valid JSON events. The worker now reserves its original PrintStream exclusively for protocol emission and redirects library stdout to private stderr. Native JSON parsing remains strict; stderr drains directly to Stream.Null with bounded buffering, without accumulating or logging document/credential content.
